# Wheel rules

These rules apply to every session working in this project.

1. Begin your first reply in a session with the line "Wheel rules loaded." alone on its own line, then a blank line, then your answer.
2. Never certify your own work. A separate session checks it.
3. Never discard uncommitted work, drop tables or delete project files with rm. The guard hook enforces this. Stash first, move files to the trash folder, ask the owner about data.
4. Commit only your own changes. Never run `git add -A` or `git add .` blindly; name the files. Never force-push and never skip hooks.
5. Keep tests green. Run them before you say a task is done, and say plainly if you could not.
6. Record what you did in the commit message: what changed, and why.
7. Ask the owner before anything hard to undo or outward-facing: pushing, publishing, deleting, sending, spending, changing shared settings.
8. Do not put secrets in any tracked file.
9. The project's main checkout stays on main and nobody works in it: every session works in its own worktree on its own branch (start one with `wcl`). The guard hook refuses edits outside `.wheel/` and branch switches in a main checkout, and the turn save never switches a branch. Only the owner can lift this, by setting `WHEEL_MAIN_OK=1` in the environment, or for a project that cannot have worktrees (its state lives in the checkout) by `"works_in_main": true` in `.wheel/config.json`; then sessions work in the main checkout and the turn save commits there with a subject naming the files, never the prompt.
10. Release advice (live projects, those with "publishes_live" in `.wheel/config.json`): at the end of a session, and when a wake finishes, run `python3 .wheel/hooks/release.py advise`. It weighs the value waiting unreleased against the cost of the gates for the project's tier (`"tier"` in `.wheel/config.json`: income, content or personal). Work still in checking, a missing migration or a red smoke check means hold; a fix is worth releasing at any tier; owner-visible work (next_session lugs) at a cheap gate means ask; small plumbing waits for a batch; income needs more value per release. If it says ASK NOW, ask the owner once, in one line: the reason and what ships. For any other answer say nothing: no nagging. If the project declares no tier, say so once and propose one.
11. At the start of a session, read the project's prioritised backlog split into build and maintain work: `python3 .wheel/hooks/lug.py top --split` (maintain is work under the "Keep ... healthy" initiative or tagged maintain; the rest is build). Say in one line what each part holds, then work on what the owner asked for; with no ask, take the top build lug, and take maintain work when the owner is away or build has nothing ready. If both parts are empty, say so and offer one thing: run the project's scout checks (`python3 .wheel/hooks/scouts.py run`, no model needed, if `.wheel/scouts/` exists) and report what they show; a failing scout is maintenance work.
12. Keep the lugs, this project's work items (.wheel/backlog.jsonl; shown in .wheel/ROADMAP.md and .wheel/BACKLOG.md). Every write names who makes it with --by. When the owner asks for new work, add a lug: python3 .wheel/hooks/lug.py add TITLE --value 1-5 --effort 1-5 --kind owner|autopilot --source "the owner's words or this session" --initiative I-### --check "how done will be proven" --reason WHY --by WHO. It sorts by value and effort; compare it with its neighbours and, if your judgment differs, place it with --above/--below ID and say why. Tag --class maintain on a lug that keeps the project healthy and current (lugs in a "Keep ... healthy" initiative are maintain already; the rest are build). Set --urgency next_session on a lug that improves something the owner uses and will see, or that he asked for by a time (it should be done before his next session); internal plumbing stays whenever (the default). Every open lug belongs to one initiative (lug.py link ID I-###); an initiative serves one agreed goal and is written to the template (lug.py initiative add: outcome, why now, scope in and out, a checkable done when), and its lugs get no autopilot budget until the owner signs it off. Move a lug's status as work proceeds (ready, doing, checking, done, or dropped/blocked) with lug.py status ID STATUS --reason WHY --by WHO, and put the lug id in your commit messages. A separate session closes autopilot lugs. Run lug.py lint and lug.py verify before you finish.
